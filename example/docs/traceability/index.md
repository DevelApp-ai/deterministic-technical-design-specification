# Traceability Matrix

This page provides a **complete, bidirectional traceability map** between:

- 📋 **MoSCoW Requirements** — the business intent captured in `docs/requirements/moscow.md`
- 📖 **Architectural Decision Records** — the *why* captured in `docs/adrs/`
- 🔒 **OPA Policies** — the automated enforcement in `policies/terraform/`
- 🔒 **.NET Architecture Policies** — the automated enforcement in `dotnet/tests/MyApp.ArchitectureTests/`
- ⚙️ **Infrastructure Code** — the actual implementation in `terraform/`, `dsc/`
- ⚙️ **Application Code** — the .NET example application in `dotnet/`

Every artefact in the repository carries machine-readable metadata (`related_requirements`,
`related_adr`, `__rego__metadoc__`) so that this matrix can be generated
automatically from the source code.

---

## Generated Traceability (ADR-0012)

Since ADR-0012, the traceability substrate is **generated, not hand-drawn**:

- **[architecture-catalog.json](../generated/architecture-catalog.json)** — the
  machine-readable catalog of every ADR, policy metadoc, and MoSCoW requirement,
  regenerated by `scripts/scan-architecture.py` and validated by
  `policies/architecture/validate.rego` in CI.
- **[traceability.drawio](../generated/traceability.drawio)** — the full
  requirement → ADR → policy → implementation diagram in drawio format
  (book diagram conventions), regenerated byte-identically by
  `scripts/generate-traceability.py`; CI fails if the committed diagram drifts
  from the catalog.

The boundary gate (`scripts/architecture-gate.sh`) additionally fails a pull
request that changes a path governed by an Accepted ADR without citing that
ADR (id `ADR-####`) in the PR description.

!!! note "The hand-drawn diagrams below are reading aids"
    The infrastructure graph in the next section predates ADR-0010 and
    ADR-0011 and is retained for reading convenience.  The application-layer
    graph further down mirrors the generated catalog for the .NET ADR series
    (ADR-0013 – ADR-0017).  The authoritative traceability view remains the
    generated catalog and drawio diagram above.

### Application layer coverage notes

- **APP-001** (DocFX) is satisfied by ADR-0013; the DocFX Markdown export is
  generated into `docs/generated/dotnet-api/` and published under
  *Application → .NET API Reference*.
- **APP-002** (architecture tests block CI) is satisfied by ADR-0014; the four
  NetArchTest policies (APP-ARCH-001/002/003, APP-SEC-001) run in the solution
  test suite.
- **APP-003 / APP-004** (Roslyn gate, deterministic build) are satisfied by
  ADR-0016 via `Directory.Build.props`, `.editorconfig`, and `global.json`.
- **APP-005** (native build-time OpenAPI) is satisfied by ADR-0015; the
  generated `docs/generated/openapi.json` is a traceable pipeline artefact
  rendered into the [API Reference](../application/api-reference.md) page.
- **APP-006** (C4 diagrams from code) is satisfied by ADR-0017 via C4Sharp.
- **APP-007** (self-describing policy metadata) is satisfied by ADR-0014; the
  `Policy.Define` literals drive `scripts/generate-dotnet-policy-docs.py`.
- **APP-008** (client SDK generation) is a *Could Have*; the build-time OpenAPI
  document that would feed NSwag already exists (ADR-0015), so the decision is
  deferred, not blocked.

## SpecTree Chain: requirement → decision → component → test → code

Since [ADR-0023](../adrs/0023-spectree-ingestion-first-class-sources.md),
SpecTree files are first-class TDS sources, closing the traceability chain
across both layers (see [ADR-0018](../adrs/0018-spectree-specification-first-ingestion.md)
for the parsers and the [metadata contract](metadata-contract.md) for the
normalized graph):

```mermaid
graph LR
    SRS[".srs — requirements<br/>(spec:M-001…)"]
    ADRS[".adr + docs/adrs/<br/>decisions (adr:ADR-00xx)"]
    AI[".ai — components<br/>(spec:TodoService…)"]
    TEST[".test — suites<br/>(spec:TodoService.tests)"]
    NET[".NET members<br/>(<spec> tags, ADR-0022)"]
    MOSCOW["moscow.md<br/>(moscow:M-001…)"]

    SRS --> ADRS
    ADRS --> AI
    AI --> TEST
    AI --> NET
    NET -->|"<spec> verified"| MOSCOW
    SRS -.->|"normalized onto one contract"| MOSCOW
```

- **Formats** — `.srs/.adr/.ai/.test/.model/.api/.ns` plus the solution
  manifest live in-tree under `spectree/specs/` (ADR-0023, decision 3),
  parsed to JSON ASTs and normalized onto the shared metadata contract
  (ADR-0019) with namespace-qualified ids.
- **Verification** — the OPA gate (`SPEC-001`, ADR-0020) enforces the
  Minotaur-Grammars validation rules over the graph in CI.
- **Composition** — the TDS composition manifest (ADR-0021) declares
  which sources assemble into the published document.
- **Application code** — `<spec>` XML doc tags (ADR-0022) trace .NET
  members back to requirements, verified against the same contract in
  the docs job.

## How Traceability Metadata Is Maintained

### In OPA policies (`__rego__metadoc__`)

```rego
__rego__metadoc__ := {
    "id": "FINOPS-001",
    "title": "Mandatory FinOps Cost-Allocation Tags",
    ...
    "related_adr":          ["ADR-0002"],
    "related_requirements": ["M-002", "M-003", "S-001", "S-002"],
}
```

### In ADR front-matter (YAML)

```yaml
---
id: ADR-0004
title: Use PowerShell DSC for Windows Configuration Management
...
related_requirements: [M-005, S-008, S-009]
---
```

### In .NET architecture policies (`Policy.Define`)

```csharp
Policy.Define("APP-ARCH-001",
    "Controllers must not depend on repository contracts directly")
```

Both infrastructure formats plus the .NET `Policy.Define` metadata are
machine-readable: the CI/CD pipeline or a custom script can parse them to
regenerate this traceability page automatically whenever policies or ADRs
change.
